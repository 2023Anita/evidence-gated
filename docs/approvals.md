# 审批：谁批准了哪一版

合同采用 JSON（`task-contract.json`），避免 YAML 多义解析。`spec` 对合同、规格、计划、基线以及治理代码计算摘要，生成 `tasks/<ID>/approval-request.json`。该文件按固定 JSON 编码生成，不能手工美化后再签。

## 默认拒绝

`workflow/policies/allowed_signers` 默认只有注释，没有任何可信批准者。
`gate --checkpoint execute` 缺少签名时返回 13，这是正常保护行为，不是安装失败。

配置批准者公钥属于治理引导步骤，由维护者在 Agent 不能修改的治理副本执行。正式私钥必须在独立人工环境；与 Agent 同账号且可以任意读取的私钥不能构成独立审批。

## 人工操作示例

以下是给批准者的操作指南，**不是让 Codex 自动执行的流程**：

1. 核对任务合同、规格、计划、基线文件、治理版本与审批请求摘要。
2. 确认请求没有改变风险、操作范围或必需证据。
3. 在独立人工环境使用已有批准者密钥签署请求。

```bash
ssh-keygen -Y sign -f "/批准者私钥路径" -n egw-spec-v1 "/审查后的/approval-request.json"
```

公钥登记格式（实际文件必须由维护者填入真实公钥）：

```text
maintainer ssh-ed25519 BASE64_PUBLIC_KEY
```

把生成的 `approval-request.json.sig` 放回对应任务目录，不把私钥带回工作区。更改签名者配置会改变治理摘要，原审批需要重新生成并签署。

## 失效条件

- 改变合同、规格、计划、基线或治理代码：旧签名失效。
- 只在批准路径内修改业务代码：规格审批保持有效，但测试必须重跑。
- 修改已测试代码：旧报告不得复用。
- GitHub base 分支发生变化：MVP 要求更新基线并重新审批。

MVP 不提供自动基线重置或强制批准开关。重新制定基线时，在新的干净工作区发起新任务，保留旧任务材料用于审计；不要手动修改基线以消除越界差异。

## 签名的限制

当前 SSH 签名验证身份和内容一致性，不提供在线撤销服务或自动到期策略。取消批准者或轮换公钥会使关联治理版本发生变化，需要更新受保护版本。临床高风险签核不能直接使用这个软件 MVP 代替专门设计。

`scripts/demo.py` 和测试生成的密钥是一次性的测试夹具，仅用于展示逻辑；它们不是用户批准，也不应该配置为正式可信身份。
